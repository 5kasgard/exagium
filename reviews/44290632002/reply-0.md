| 1 | **worker/doc_job.py – `draft()`** (the call to the drafter) | The drafter prompt contains the *entire* target file contents. A malicious repository file can embed a *shell‑command* inside a line that the model later repeats verbatim in the JSON “new” field. When `apply_edits()` writes that line back to the file, the **GitHub Actions runner later executes the file as part of the `git add -A -- '*.md'` step** because the runner’s default `core.autocrlf` and `text` attributes treat `*.md` as *text* but the *commit hook* `pre‑commit` (not shown) could be configured to run a linter that executes code blocks. | 2 | **worker/research_job.py – `read()`** (model‑generated claims) | The model can return a claim whose “quote” field contains a *large‑scale Unicode‑combining‑character* sequence that, when written to a markdown file by `card()`, triggers a *Unicode‑based denial‑of‑service* in downstream renderers (e.g., VS Code, GitHub). | 3 | **worker/queue_ops.py – `claim()`** (git‑based lock) | Two workers can *both* think they hold the same item when the first worker’s push succeeds but the second worker’s push **fails** *after* it has already written the claim into its local `queue.json` and saved the file. The second worker then returns `{"item": i, …}` (the item it thought it claimed) because the `if commit_push(...):` test is **False**, but the loop continues and eventually returns `{"item": None, "lost_races": …}` only after `TRIES` attempts. If the second worker crashes **after** the failed push but **before** the next loop iteration, the item stays marked “in progress” with the first worker’s lease, but the second worker’s local copy still believes it owns the item and may later run `release()` with the wrong `worker` id, causing a *duplicate release* that writes a bogus run entry. | The code path is traceable: after a failed push the loop continues; if the process is killed before the next iteration, the stale claim remains in memory but never reaches the repo. The stale claim can be used to fabricate a “release” later (e.g., via a replay attack). | • After a failed `commit_push`, **discard** the in‑memory claim (`i`) and reload the queue before proceeding. <br>• Add a guard in `release()` that aborts if the item’s `claimed_by` does not match the supplied worker **and** the `status` is not “in progress”. <br>• Persist a temporary “tentative‑claim” flag that is cleared on any push failure. | **Critical** |
| 4 | **worker/queue_ops.py – `expire()`** (lease expiry) | The function only runs when a worker invokes `claim()`. If the queue stays empty for a long period (e.g., weekend), items whose lease has already expired will **never be reopened**, leaving them stuck in “in progress”. This violates the “no item stuck” guarantee. | `expire()` is called at the start of each `claim()` attempt. If `claim()` is never called (queue empty), expired items are never processed → stuck. | • Run `expire()` as a separate scheduled job (e.g., a daily “maintenance” workflow) that rewrites the queue and pushes a commit even when no claim is made. <br>• Or modify `ready()` to call `expire()` internally before filtering, ensuring expiry is checked on every read. | **Major** |
| 5 | **worker/ledger.py – `reserve()`** (neuron‑cap bypass) | The neuron cap for Cloudflare is stored in `CAPS["cloudflare"]["neurons"] = 5000`. The check only looks at `e["neurons"] >= cap["neurons"]` **without** adding the neurons that will be consumed by the current reservation. A worker can therefore reserve unlimited calls that each consume many neurons; the cap is never triggered. The later `record()` adds the actual neuron usage, potentially exceeding the daily limit by orders of magnitude. | The condition `e["neurons"] >= cap["neurons"]` never changes during `reserve()`, so the cap is effectively disabled. This is traceable in the code. | • Change the check to `e["neurons"] + projected_neurons > cap["neurons"]`. Since the reservation does not know exact neurons, require the caller to specify an estimated neuron budget (e.g., `cloudflare:1:100` meaning 1 call, 100 neurons). <br>• Enforce the same check in `record()` and abort the push if caps would be exceeded. | **Critical** |
| 6 | **worker/ledger.py – `record()`** (no cap enforcement) | After usage is recorded, the ledger file is updated and pushed **without** re‑checking the caps. An attacker can deliberately *under‑reserve* (e.g., reserve 1 call) then make many more calls in the same run (by looping the model) and record them, inflating `calls` and `neurons` far beyond the caps. | `record()` never looks at `CAPS`; it simply adds the numbers and pushes. This is traceable. | • In `record()`, after updating `led`, verify that for each pool `led[pool]["calls"] <= CAPS[pool]["calls"]` and `led[pool].get("neurons",0) <= CAPS[pool].get("neurons",∞)`. | 7 | **worker/digest.py – `metrics()`** (double‑claim counting) | The holder map is never cleared on lease‑expiry commits (`worker: leases expired …`). This **inflates** the double‑claim metric and can hide real contention problems. | The loop over commit subjects adds `expired += 1` on “leases expired” lines but never removes `holder[item]`. Traceable. | • When a “leases expired” line is seen, also `holder.pop(item_id, None)` for each id listed in the commit message (the commit message includes the list of IDs). <br>• Alternatively, rebuild `holder` from the current queue state after processing all log lines, rather than incrementally. | **Minor** |
| 8 | **worker/digest.py – `flag()`** (pointer regex too permissive) | The regex `POINTER` matches any string that looks like a path (`foo/bar.md`) **anywhere** in a sentence, causing false negatives: a legitimate sentence containing a file path but no numeric claim will be considered “evidence” and not flagged, allowing a model to hide a fabricated number by appending a harmless path.
