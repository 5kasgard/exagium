1: # forge-probe — spec card
2: 
3: **What it is.** The first brick: a tool that measures a machine's invariants and writes `profile.json`. It records memory latency at each working-set size, the memory levels fitted to that curve, read bandwidth, compute ceilings, timer quality, host interference, and which meter tiers the machine offers. Every number is labelled **measured** (timed here), **reported** (the OS or CPU's claim) or **derived** (computed or fitted from measured numbers).
4: 
5: **Run.**
6: ```
7: python3 probe.py                      # full: ~100 s on 2 vCPUs, 7 reps, sweep to 4x reported LLC (cap: 1/4 of free RAM)
8: python3 probe.py --quick              # ~10 s smoke run, 3 reps, coarser sweep
9: python3 probe.py --reanalyse p.json   # recompute from raw reps; exit 0 consistent, 1 inconsistent,
10:                                       #   2 consistent but meter claims unverifiable (different host)
11: python3 -m unittest -v test_probe     # 40 tests, ~65 s
12: ```
13: Needs a C compiler and Python 3 (stdlib only). Linux. Valgrind is optional and detected as a tier.
14: 
15: ## What it measures
16: | Measurement | How | Bound by |
17: |---|---|---|
18: | Latency per working set | Dependent pointer chase over one random cycle of cache lines (Sattolo), √2 size steps from 4 KiB, new permutation every rep | load-to-use latency of whichever level holds the set |
19: | Read bandwidth | 8 independent 64-byte-vector accumulators; L1-sized and DRAM-sized buffers; 1 thread and all threads | loads (L1) / memory system (DRAM) |
20: | Compute ceilings | 16 independent FMA chains: scalar f64, vector f64, vector f32; 1 and all threads. The build's vector ISA is recorded (`build.vector_isa`) | FMA issue rate on that ISA |
21: | Timer | smallest observable step between reads, read cost, and the kernel's `clock_getres` claim | — |
22: | Host interference | CPU steal per rep from `/proc/stat` | — |
23: | Meter tiers | Each one is tried, not assumed: RAPL zone read; CPU PMU in sysfs and then `perf stat`; NVML library and then `nvidia-smi`; a cachegrind run; tier-3 calibration file | — |
24: 
25: **Noise.** Each rep runs every measurement once in a freshly shuffled order (the seed is recorded), each in a fresh process. Every figure carries n, median, bootstrap SE of the median, mean, SD, SE, CV, min and max. With a single rep, every spread figure is `null`, and no levels are fitted.
26: 
27: **Memory levels (derived).** No cache sizes are assumed.
28: 1. **Physics first.** Latency can't fall as the working set grows. A point significantly slower than the next kept size is interference: it is excluded and listed (`memory_levels_excluded_bytes`). If more than 20% of the curve breaks this, no levels are fitted, and the profile says why.
29: 2. **Fit.** A piecewise-linear fit of log latency on log size, with each point weighted by its own noise, widened to Student-t tails because it comes from few reps. Real plateaus drift a little, so a plateau is one sloped segment.
30: 3. **What counts as a level.** A segment spanning at least 2× in size, where at each edge:
31:    - the edge steps *up* toward larger sizes;
32:    - its fitted rise is significantly less than half the jump. "Significantly" uses the owner's 2-SE rule, Bonferroni-corrected because the breakpoints come from the data;
33:    - the plain spread of its interior medians is under half the jump. Weighting can't hide this check, and the end points are excluded because that's where reps mix at a boundary;
34:    - its slope is under half the edge's slope, so a long ramp is never taken for an edge.
35: 
36:    A lone segment must show no detectable rise.
37: 4. **Merging.** Two neighbours are merged only when the step between them is under half the outer jumps, each measured from that piece's own line, and the result still passes as a level.
38: 5. **Capacity brackets.** A bracket runs from the last size where no rep had yet reached the next level to the first size where no rep was still at this level. If no next level was found, the upper end is `null` (unknown), never "end of sweep". **A bracket covers what these reps showed. It isn't a confidence interval for the true capacity.**
39: 6. **Sweep reach.** `sweep_reach` warns when the sweep stopped below 2× the reported last-level cache (it is RAM-limited), because DRAM may never have been reached.
40: 7. **Explicit choices** are stored as structured fields in `memory_levels_choices`: 2× span, ½ ratio, 20% exclusion cap.
41: 
42: Every doubt resolves toward "transition", never toward "level", and each level reports its own `rise_across_span`.
43: 
44: **Simulated error rates.** Run through the tool's own reps → bootstrap → fit path on three independent noise generators: mine, GLM-5.2's (Student-t noise, interference spikes, drift), and a fresh Claude reviewer's (soft random-replacement transitions, off-grid capacities, per-level noise, correlated noise, per-rep capacity jitter). 200 seeds each.
45: 
46: | Case | Phantom level | False boundary | Wrong value/bracket | Exact recovery |
47: |---|---|---|---|---|
48: | 4 levels, 7 reps: lognormal, Student-t, drift, rampy, off-grid hard steps | 0% | 0% | 0 | 100% |
49: | 4 levels, 7 reps, heavy-tailed (10% outliers at 1.5–3×) | 0% | 0% | 0 | 85.5% |
50: | 4 levels, 7 reps, very different noise per level / one precise level beside noisy ones | 0% | 0% | 0 | 99.5% |
51: | 4 levels, 3 reps (`--quick` sweep) | 0% | 0% | 0 | 99–100% |
52: | 4 levels, 3 reps, heavy-tailed or Student-t(2) | 0% | 0% | 0 | 63–72.5% (misses only) |
53: | Drifting precise plateaus, 7 reps / 3 reps quick | 0% | 0% | 0 | 100% / 100% (of 100) |
54: | Flat curve, 12 / 34 points | 0% | 0% | 0 | 93.5–97.5% |
55: | Ramps (1–5%/step, 2–5% noise; a curved precise ramp; alternating slopes; a bump in a ramp) | 0% any level | 0% | — | — |
56: | Noise correlated across neighbouring sizes | 0% | 0% | 0 | 21–40%; refuses 45% (the safe failure) |
57: | **Interference spikes:** 10% of sizes, every rep slowed 3× | 0% | 0.5% | **12.5%** | 73% |
58: | **Capacity varies per rep** (15–30%), 3 reps | 0% | **11–18.5%** | — | 70.5% (7 reps: 0.5% wrong) |
59: | **Soft transitions** (hit rate = capacity ÷ size, as in random-replacement caches), 7 reps | 0% | **15.5%** | value 19% | 5% |
60: 
61: **Known limits** (the bold rows above):
62: - **A spike on the last point of a level** looks exactly like the start of the next level, so the bracket ends one grid step early. No method can tell them apart using this data.
63: - **With 3 reps, a bracket only covers what 3 reps showed.** When capacity varies from rep to rep (page placement in physically indexed caches), it misses the true capacity by up to 1.38×. Use 7 reps for brackets.
64: - **Under soft transitions there is no clean plateau after a capacity.** Brackets miss by up to 1.45×, and a level's value is a mixture of two levels. Fitting a soft-transition model is the next improvement to test.
65: 
66: **What `--reanalyse` can and can't show.** It recomputes every statistic from raw reps and checks the following:
67: - the rep counts match the settings;
68: - each rate equals its own recorded work ÷ time;
69: - each timed window is at least its minimum;
70: - each chase seed matches the run seed;
71: - on the same host, it re-detects every meter tier.
72: 
73: On another host it exits 2.
74: 
75: **Digests, for the record to anchor.** Each profile carries `digests.profile_sha256` (the whole profile) and `digests.measurement_sha256` (raw reps, settings, build, environment, meter tiers, time). Both are sha256 over canonical JSON: sorted keys, no whitespace, UTF-8, and no field joining. A run prints the profile digest at the end, and `--reanalyse` recomputes it. Once a digest is anchored somewhere outside (open item 3), any later edit shows up as a different digest. A digest proves only that the profile hasn't changed since anchoring, never that it's genuine; independent re-measurement (open item 4) is what tests genuineness. The scheme uses Python's float formatting, which isn't yet RFC 8785 (JCS), so another language must match it to reproduce a digest.
76: 
77: > **It can't detect forgery.** Anyone can fabricate a raw section that is self-consistent and holds any numbers at all. An independent verifier forged 1.5× compute, 2× bandwidth and 0.5× latency, and all of them passed. Only an outside-anchored record (open item 3) can stop that. CPU steal, timer readings and the recorded seed (rewriting it and every chase seed together stays consistent) can't be checked against anything either.

1: # counter — spec card
2: 
3: **What it is.** The second brick: it runs a command under `valgrind --tool=cachegrind` several times and records the instruction and simulated cache-miss counts. This is the deterministic half of meter tier 2 (timing is the other half). Every count is labelled **simulated**. Cachegrind replays the program on a model CPU and a model cache; it reads no hardware.
4: 
5: **Run.**
6: ```
7: python3 count.py -- /abs/or/PATH/program args              # 3 reps, reference cache, record in ../runs/
8: python3 count.py --input net.py --input w.bin -- python3 net.py
9: python3 count.py --input cand -- ./cand 1000               # ./name must be an --input
10: python3 count.py --check ../runs/<record>.json [--input-dir DIR]
11: python3 -m unittest -v test_count                          # 23 tests, ~34 s
12: ```
13: **Exit codes:**
14: - **0:** counted, every rep identical in counts and output, and no code found that can switch counting off. With `--check`: same counts, processes and output, still clean.
15: - **1:** reps differ in counts or output, or such code was found. With `--check`: counts or output differ, or the record was edited or is malformed.
16: - **2:** `--check` can't compare like for like: a record from another version of `count.py`, another program, input, interpreter, shared library, loader cache, valgrind build, architecture or cache model; or the recorded run itself wasn't a clean exact count.
17: - **3:** the command or valgrind failed, a process called `exec` (below), or anything unexpected happened. A failure is never reported as a verdict.
18: 
19: Needs Linux, Python 3 (stdlib only) and valgrind 3.22 or later. CI installs it with `apt install valgrind`.
20: 
21: ## How a run is isolated
22: Each rep starts from a **fresh sandbox at a fixed path**, `/tmp/exagium-count`:
23: - an empty working directory holding only the declared `--input` files;
24: - an empty `HOME` and an empty `TMPDIR`.
25: 
26: The path is fixed because path strings themselves change counts (below). A lock file lets one counter at a time use it.
27: 
28: **The environment is fixed byte for byte.** The command sees only:
29: - `PATH=/usr/local/bin:/usr/bin:/bin`, plus `HOME` and `TMPDIR` in the sandbox;
30: - `LC_ALL=C`, `TZ=UTC`, `PYTHONHASHSEED=0`;
31: - one thread for OpenMP, OpenBLAS and MKL;
32: - anything added with `--env`. `PATH`, `HOME`, `TMPDIR` and anything starting `VALGRIND_`, `LD_`, `GCONV_PATH` or `GLIBC_TUNABLES` are refused, because they could swap the cachegrind tool or load unfingerprinted code (review 2).
33: 
34: **Valgrind:**
35: - `--command-line-only=yes`, so `.valgrindrc` files and `VALGRIND_OPTS` are ignored (tested).
36: - `--trace-children=yes`, with counts summed over every process.
37: - **One log on a pipe.** Every process logs to one pipe, on a file descriptor valgrind reserves. Unlike a file, a pipe can't be edited afterwards. Each process image writes a `Command:` header when it starts, and every process, forked children included, writes its `I refs` total when it ends. The counter requires exactly one count file per reported total, with the same `Ir`. A deleted count file, or one whose `Ir` was edited, is therefore a failure, and so is a process that outlives the command.
38: - **`exec` is refused, by the command or by any child.** Valgrind drops the counts of a process image when it calls `exec`, so work before an `exec` would vanish. Review 2 measured a ~1,500× undercount, and ~860× from a fork child that did the work and then exec'd. Only the command itself may start a process image, so any second `Command:` header is a failure.
39:   - **Allowed:** children made by `fork` alone, such as Python `os.fork` or multiprocessing with fork.
40:   - **Refused:** shells, `subprocess` spawns, `posix_spawn` and `#!/usr/bin/env` scripts. Run programs directly, e.g. `python3 script.py`.
41: - All three caches are always passed. Given only `--LL`, valgrind would take I1 and D1 from the host's CPUID.
42: 
43: **What's executed is fingerprinted.** sha256 is recorded for:
44: - the program, and its `#!` interpreter if it's a script;
45: - every shared library `ldd` resolves for them;
46: - every input;
47: - the host's `/etc/ld.so.cache`;
48: - the valgrind launcher, the cachegrind tool binary and `count.py` itself.
49: 
50: These files are also scanned for the **valgrind client-request preamble** (x86-64 and arm64). That code can switch counting off (`CACHEGRIND_STOP_INSTRUMENTATION`) or detect valgrind. If it's found, the run exits 1. A test shows the stop request really does hide about 3 million instructions, and that the scan flags it.
51: 
52: ## What it records
53: One JSON file per run in `runs/`, opened with exclusive create, so a record is never overwritten. Each record holds:
54: - the command, environment, inputs and fingerprints;
55: - the valgrind version and options, and the host (CPU model, kernel, libc, loader-cache digest);
56: - the cache model requested and the one actually simulated (a mismatch is a failure);
57: - every rep's counts (`Ir`, `Dr`, `Dw`, and L1 and LL misses for instructions, reads and writes), its process count, wall time under valgrind, and the sha256 of its stdout;
58: - the median, min, max and relative spread of each count;
59: - the verdict: `exact`, `stdout_identical` and `client_request_code`;
60: - caveats, and a sha256 digest of the canonical record. The digest is an integrity checksum, not a seal, since anyone can recompute it.
61: 
62: ## Reference cache (an explicit choice)
63: | Cache | Size | Ways | Line |
64: |---|---|---|---|
65: | I1 | 32 KiB | 8 | 64 B |
66: | D1 | 48 KiB | 12 | 64 B |
67: | LL | 8 MiB | 16 | 64 B |
68: 
69: This is a convention for comparing candidates across hosts. It doesn't model any one host. Why these sizes:
70: - **D1 48 KiB.** Machine C's VM reports 32 KiB, but the probe measures 1.55 ns at 44 KiB (`runs/probe_C_20261110.json`). Machine A's level 1 also covered 4–44 KiB (probe spec card).
71: - **LL 8 MiB.** On machine C, the curve sits at 25 ns up to 5.9 MiB and is DRAM-like at 8 MiB. Machine A's spec card gives its one-core last level as 8–16 MiB.
72: - **Shape.** Valgrind needs a power-of-two number of sets: 64 for D1, 8192 for LL.
73: 
74: `--cache host` uses CPUID instead. That gives a different model on every host, so its counts are only comparable on the same host.
75: 
76: ## Hypothesis 1: are the counts reproducible?
77: **Within one host: yes, for deterministic programs.**
78: - **C** (a small MLP, `workloads/mlp.c`): every rep identical, in all 88 CI records and every run here.
79: - **Pure Python:** without a fixed hash seed, `Ir` varied by 0.3% between reps. With `PYTHONHASHSEED=0` (the default), every rep was identical.
80: - **NumPy (OpenBLAS):** reps still varied by 2–8 × 10⁻⁶ with one thread and a fixed hash seed, with or without ASLR. `cg_diff` places the difference in interpreter code (dict resizing, memcpy). The cause isn't traced.
81: - **ASLR** changed nothing for C or pure Python (`setarch -R` gave identical counts).
82: - These single-host numbers are reproducible with `experiments/h1_local/run.sh`; its output is `h1_local.txt` (made before the sandbox, so it toggles each factor by hand).
83: 
84: **Across hosts: the CPU never mattered.** Valgrind presents its own synthetic CPU to the program. Here it was an Intel signature `0x306c3` with AVX2 and no AVX-512, while the host has AVX-512. So code that dispatches on CPU features takes the same path on every AVX2 host.
85: - **Totals, same binary and image:** identical across six x86-64 CPU models. AMD: EPYC 7763, 9V74 and 9V45. Intel: Xeon 8573C, 8370C and 6973P-C. A seventh, Xeon 6975P-C, ran only once, on its own image (review 2).
86: - **arm64:** Neoverse N2, CPU part `0xd49`. Every arm64 job gave the same total.
87: 
88: **What moves the totals is software and setting, all at startup:**
89: - **The runner image:** for example, 36,018,926 vs 36,018,955 `Ir` for `./mlp 1000` on two images.
90: - **Path and environment strings:** the working directory changed Python's `Ir` by 7 × 10⁻⁵ to 1.3 × 10⁻⁴, and `HOME` changed C's `D1mr` by 2–3. That's why the sandbox path and environment are now fixed.
91: - **This workspace** (machine C, another kernel) gives 36,018,927: one instruction off the CI value.
92: 
93: **The program's own work is what reproduces.** Subtract a startup-only run (`n` = 0) from the full count. With the sandbox (CI run 41988500105 plus this workspace):
94: 
95: | Workload | Hosts | Count minus startup |
96: |---|---|---|
97: | C, x86-64 | 4 CI jobs, 3 images and 3 CPU models, plus machine C | 35,765,911 on every one |
98: | C, arm64 | 4 jobs, 2 images | 30,898,727 on every one |
99: | Python, x86-64 | 2 Azure images | 40,676,904 on both |
100: | Python, x86-64 | AWS image (another loader cache) | 40,701,411 (6 × 10⁻⁴ off) |
101: | Python, arm64 | 2 images with the same fingerprint | 41,774,558 vs 41,774,514 (1 × 10⁻⁶) |
102: 
103: **So:**
104: - **C:** counts are reproducible across hosts once startup is subtracted.
105: - **Python:** the interpreter reads image files that the fingerprint doesn't cover (inferred, not traced). Its counts are comparable only within one image.
106: - **`--check`** returns 2 (can't compare) when the loader cache differs, as with the AWS image. It can't detect a difference that leaves the loader cache unchanged, as with the arm64 pair.
107: 
108: **Where the clean environment is defeated:**
109: - **`python3 -I`** ignores every `PYTHON*` variable, including the hash seed. Every CI job then reported reps that differ (16 of 16), and the verdict flagged each one. My hypothesis that isolated mode would remove image dependence was refuted.
110: - **Any program that reads randomness, the time or the host** varies, and the verdict says so; the test `noisy.c` confirms it.
111: 
112: ## Hypothesis 2: how far are simulated misses from the measured latency curve?
113: Machine C, probe run seed 20261110. The same Sattolo chase ran at the probe's 32 sizes, under cachegrind, with steady-state misses per load. Script: `experiments/sweep.py`.
114: - **Two levels, sharp edges.** The model has L1 and LL only, with LRU, so for a cyclic chase every size gives exactly 0 or 1 miss per load. Real latency rises in steps with mixed points.
115: - **Host model** (CPUID: D1 32 KiB, LL 34 MiB): the simulated level matches the measured one at 26 of 32 sizes.
116:   - At 44 KiB the model misses D1, but the hardware is still at L1 latency (1.55 ns).
117:   - At 8–33.5 MiB the model hits LL, but the hardware is at DRAM-like latency (94–161 ns).
118: - **Reference model:** 31 of 32 match. The only miss is exactly 8 MiB, which fits the model's LL but measures 161 ns.
119: - **L2 is invisible.** The measured L2 (64 KiB–1 MiB, 4.3 ns) and the 25 ns region at 1.4–5.9 MiB are both just "D1 miss, LL hit".
120: - **Machine A**, by arithmetic only, from its spec card: its VM reports a 260 MiB L3, so a host model would call everything up to 260 MiB an LL hit. The probe measured DRAM there from 16 MiB.
121: 
122: **So the counts are a deterministic work measure, relative to a stated model, not a latency predictor.** Turning counts into time or joules is calibration: tier 3, open item 5.
123: 
124: **Found along the way:** counting only a region (client requests with `--instr-at-start=no`) starts with a cold model cache, so every line misses once. The sweep removed this by differencing two lap counts.
125: 
126: ## What `--check` can and can't show
127: **Before re-counting,** it requires that:
128: - the record's digest and internal consistency hold (malformed → 1, never a crash);
129: - every input, the program, interpreter and shared libraries, the loader cache, the valgrind version and the architecture match (otherwise 2).
130: 
131: It then re-counts in the fixed sandbox and compares counts, process count and stdout.
132: - **Catches** (tested): an edited record, and a self-consistent forged record with a recomputed digest, because re-counting gives different numbers.
133: - **Can't show** that a record was made on the host it names, or when. That needs the record and its outside anchor (open item 3).
134: - **Can't tell an image difference from a forgery** when the loader cache is the same (the arm64 Python case). Both exit 1.

164: ## Trust model
165: Cachegrind runs inside the candidate's own process, as the same user. **Hostile native code can therefore always falsify its counts.** Known ways that still work:
166: - edit the cache-miss fields of a count file (only `Ir` is cross-checked against the pipe);
167: - have a forked child do the work and then have its parent kill it with `SIGKILL`, so it never reports (review 2: Ir 132,941, exit 0);
168: - append forged lines to the log pipe through `/proc/self/fd` (no undercount found this way yet);
169: - write into valgrind's memory;
170: - build code at run time that the client-request scan never sees. Review 2 decoded a stop-counting binary from a base64 input and ran it: Ir 1.07–1.31 M instead of ~250 M.
171: 
172: So the counts are trustworthy for code that isn't trying to cheat. Against code that might be, they are a claim, not proof. The cross-checks are:
173: - the timing half of tier 2;
174: - output checked against expected answers;
175: - independent re-measurement by someone else (item 4);
176: - running untrusted candidates in a fresh container, as another user, with the counter outside it. That is the next isolation step, and an inbox item.
177: 
178: A clean scan (`client_request_code: []`) means only that no such code was found in the files scanned. It is not evidence that counting stayed on.
179: 
180: ## Known limits
181: - **Not a container.** A program can still use absolute paths outside the sandbox (a cache left in `/var/tmp`, say), other processes, or the network. Run untrusted candidates in a fresh container; CI does, since each job is a fresh VM. The verifier must also check the output against the expected answers.
182: - **Code loaded later isn't scanned:** `dlopen`, JIT, and code decoded at run time (see the trust model).
183: - **The synthetic CPU.** Counts are for the AVX2-or-lower path. On AVX-512 hosts that isn't the path that runs natively.
184: - **Threads.** Valgrind runs one thread at a time, and thread counts are pinned to 1.
185: - **Speed.** About 20–100× slower than native.
186: - **Platforms.** Tested on Linux x86-64 and arm64 with valgrind 3.22 only. No branch simulation.

--- FILE: loop/README.md ---
1: # loop — spec card
2: 
3: **What it is.** The fourth brick, and the first loop: small classifiers for one task, scored against two mandatory cheap baselines on the project's meter (tier 2: simulated instructions and native time). One agent proposes candidates and a pre-registered plan; the plan goes into the ledger before the test set is touched; a separate agent runs the test and judges it by the plan's own rule; the verdict goes into the ledger.
4: 
5: **Run.**
6: ```
7: python3 loop.py freeze DIR...                      # digests for a plan's "inputs"
8: python3 loop.py reproduce DIR...                   # retrain in the jail; weights must be byte-identical
9: python3 loop.py evaluate DIR... --test dev         # smoke test (in-sample for anything trained on the whole file)
10: python3 loop.py evaluate DIR... --test test --plan SEQ [--rounds R] [--seed S]
11: python3 -m unittest -v test_loop                   # 20 tests, ~20 s (1 skipped under bubblewrap)
12: ```
13: Exit codes: 0 done; 1 a check failed; 2 bad arguments (e.g. `--test test` without `--plan`; the docstring omits this); 3 failure. Plan 2 froze `loop.py`, `timer.c`, `counter/count.py`, `record/record.py`, the task and the candidates. `record.py` changed after entry 4 (a fix found by Z), so re-measure plan 2 at commit `113a3f6`, the last one with every frozen file unchanged. Needs Linux, gcc, valgrind 3.22+, bubblewrap with unprivileged user namespaces or else Linux 6.7+ for the fallback jail, Python 3 (stdlib; candidates' `train.py` may use `numpy==2.5.3`).
14: 
15: ## The task
16: UCI optdigits (`task/SOURCE.md`): 8×8 images of 0..16 pixel counts, 3,823 training rows from 30 writers, 1,797 test rows from 13 other writers. The **dev** split is the last 25% of the training file. It is the holdout the baselines use to choose their L2 strength, so it's in-sample for anything refit on the whole file: a smoke test only.
17: 
18: ## A candidate
19: A directory holding exactly `train.py`, `infer.c` and `weights.bin` (plus an optional README that its code never sees):
20: - `python3 -s -P train.py train.csv weights.bin` must be deterministic;
21: - `./infer weights.bin x.bin N` prints N digits and a newline; `x.bin` is N rows of 64 bytes. N = 0 is startup only;
22: - compiled with `-O2 -std=c11 -ffp-contract=off`, no `-march`, from a copy.
23: 
24: **Baselines** (`baselines/`): `linear`, logistic regression on pixels/16; `thermo`, thermometer encoding (16 bits per pixel) plus logistic regression, run as a 64×17×10 lookup table. Both pick L2 on dev, then refit on all rows.
25: 
26: ## What a score is
27: For each candidate, on one machine, in one `evaluate`:
28: - **Accuracy** on the split, and **paired** differences against every other candidate, with SEs from per-image differences. Images are treated as independent; the test set has 13 writers, so true SEs are larger.
29: - **Simulated instructions per image:** `counter/count.py` (reference cache) counts *one* process classifying all N images, divided by N. Startup is included, so no work can escape the count by moving to N = 0. The N = 0 count is shown as "marginal", informational only.
30: - **Native ns per image:** the same one-process run, timed inside the jail by `timer.c` (pinned to one CPU). R rounds, candidates in a fresh random order each round, rows freshly shuffled each run. Predictions of every timed run and the counted run must agree, after undoing the shuffle.
31: - **Cross-checks:** time per simulated instruction more than 30× the lowest candidate's is flagged. The scoreboard JSON carries `valid`: false whenever any check raised a problem.
32: - **Meter disagreements** (`cost_disagreements`, printed as `METERS DISAGREE`): every pair where one candidate uses fewer simulated instructions yet is slower natively past 2 SE (paired, interleaved rounds). These aren't problems with the run; they mark where an instruction-count cost claim alone would be wrong.
33: 
34: **The test set is gated.** `--test test` refuses unless the ledger verifies and its anchors check, entry SEQ is a plan whose `inputs` hold every digest `freeze` gives now (task files, `loop.py`, `timer.c`, `count.py`, `record.py`, every candidate file), and every candidate's training reproduces its weights byte for byte, in the jail, here.
35: 
36: ## The jail
37: All candidate code (training, the counted run, the timed runs) runs in bubblewrap:
38: - a fresh tmpfs `/tmp`, read-only `/usr`, no network, its own PID and IPC namespaces;
39: - uid 65534 with every capability dropped, and a fresh session keyring;
40: - a working directory holding only that step's files. The repo, the test file and the frozen weights are not in it;
41: - files named like the dataset (`optdigits*`, `digits.csv*`) under `/usr` and the Python prefix are masked.
42: 
43: **One process, one thread.** The counter (`--single-process`) and the timer both read the jail's PID namespace `ns_last_pid` before and after a run, and refuse unless exactly one pid was handed out. That catches a child killed before it reports, an unreaped child and a thread alike. The jail can't write that file. The timer also requires the child to be the very next pid, so a pid wrap can't hide one.
44: 
45: ## The fallback jail (when bubblewrap can't run)
46: Stock Docker, Kubernetes and some VMs refuse unprivileged user namespaces, so bubblewrap can't build its jail. `loop.py` then falls back to **confine** (`confine.c`, `seccomp_filter.h`), which needs no privilege at all. The mode is chosen at start-up by a self-test (bubblewrap first), recorded in every output as `"jail"`, and can be forced with `EXAGIUM_JAIL=bwrap|confine`.
47: - **Files (Landlock ABI 4+, Linux 6.7+; `confine` refuses older ABIs, which leave truncate or TCP outside Landlock):** reads are allowed only on a list carved around the dataset copies. A directory on the way to a hidden file can be listed but not read through; a symlink is granted only if its real path doesn't lead to a hidden file (site-packages is a symlink on Debian and Ubuntu). Writes go only to the step's own directories (under the counter, also its sandbox and count files, which it cross-checks). No TCP.
48: - **Everything else (seccomp):** no fork, clone, sockets, keyring, ptrace, signals to other processes, namespaces, mounts, io_uring, BPF or perf. No SysV IPC or POSIX message queues, and no chmod, chown, utimes or xattr writes, because those outlive a run and Landlock doesn't cover them. Rlimits, CPU affinity, priority and scheduling only on the process itself: the harness shares its uid and pid namespace, so a nice value set on `loop.py` would slow every later timed run. An outside reviewer found the IPC hole independently, our own review the metadata hole, and a separate fact-check agent the rlimit and priority hole (its test fails on the old filter).
49: - **The meters, almost unchanged.** The timer runs under Landlock only, so Landlock's setup (about 630 rules) isn't timed; the seccomp filter is installed in the timed child just before `exec`, a small cost bubblewrap runs don't pay (not yet measured). The counter wraps valgrind in confine with the same lists, plus `/proc/self` and `/proc/cpuinfo` (valgrind needs them). bubblewrap's one-pid check is replaced by seccomp refusing every way to make a process or thread.
50: 
51: **Results** (`test_loop`, 20 tests: the attacks from rounds 1, 2 and 4 replayed, plus network, keyring, fork, IPC, metadata, rlimit, priority, affinity and scheduler attempts; ptrace, namespaces, mounts, io_uring, BPF and perf are denied but not separately tested):
52: - **H1, it refuses what bubblewrap refuses:** holds. Every test passes in both modes, here and in stock `ubuntu:24.04` Docker on x86-64 and arm64 (the `docker` job in `loop.yml`).
53: - **H2, same programs, same counts:** holds on the same host: Ir/img is identical in both modes. Between Docker's image and the runner's, only process startup differs (−413 Ir per run on x86-64, −175 on arm64), so compare Ir across hosts with the same OS image.
54: - **H3, it works where bubblewrap can't:** holds in stock Docker. Not on Z's kata sandbox: its kernel (5.10) predates Landlock, so neither jail runs there and `loop.py` fails closed.
55: 
56: **Limits of the fallback** (bubblewrap has none of these):
57: - `stat()` still reveals that a hidden file *exists*; only reading it is refused. Dataset copies are masked by name, as under bubblewrap.
58: - Candidate code runs as the harness's own uid, not 65534 (as root in CI's Docker job; Landlock and seccomp bind root too). It can't write or signal outside its directories, but it can read whatever the allow-list grants.
59: - Reading a file can update its access time, a weak channel that `relatime` mounts mostly close.
60: - A hostile candidate that stalls (for example, one that retries fork) costs time until the step's timeout. That is a slow failure, never a better score.

71: ## Two meters, and why both count
72: Simulated instructions are a deterministic work count; they are not a cost. Plan 2's own data shows the gap. Native time per simulated instruction, startup removed, from the committed scoreboards:
73: 
74: | | EPYC 7763 | arm64 |
75: |---|---|---|
76: | linear | 0.089 ns | 0.077 ns |
77: | thermo | 0.094 ns | 0.075 ns |
78: | mlp16 | 0.224 ns | 0.145 ns |
79: | mlp32 | 0.228 ns | 0.143 ns |
80: | mlp64 | 0.214 ns | 0.145 ns |
81: 
82: An MLP instruction took 1.9–2.6× as long as a baseline one. mlp64 used 0.43× linear's instructions on x86-64 (0.65× on arm64), yet it was slower than linear or thermo, past 2 SE, on all 7 hosts that scored plan 2.
83: 
84: **What explains it** (tested 2026-11-11 on the same data, after the fact, so hypotheses only):
85: - **Cache misses: not enough.** Adding simulated L1 misses to instructions cuts the error of a per-host fitted time model (5 candidates, so easily overfitted) from 30–46% to 22–32%. mlp16 has almost no misses (2.4 per image) yet the same high time per instruction.
86: - **Branch mispredictions: not for mlp16.** Cachegrind's branch simulator gives mlp16 3.7 mispredictions per image against linear's 4.1. mlp64 has 14.6, which may explain part of its gap.
87: - **Instructions per nanosecond: the leading hypothesis.** On the EPYC, linear retires about 11 simulated instructions per ns, the MLPs about 4.4–4.7 (the clock speed isn't recorded, so this isn't stated per cycle). A plausible cause is chains of dependent table lookups. Neither instruction counts nor cachegrind can see this; hardware counters (`perf`) can, and no host so far exposes them. Testing it is part of calibration on real hardware.
88: 
89: **The rule for every plan from now on.** A cost claim of candidate X over baseline B must pass both meters:
90: 1. **Simulated instructions,** per architecture: Ir_X / (acc_X − 2·SE(acc_X)) < Ir_B / acc_B. This is plan 2's form; it lets accuracy noise count only against the candidate.
91: 2. **Native time,** on every host that scores the plan, each judged on its own: X's paired `ns_per_image_diff` against B is below −2 × its SE. There's no averaging across hosts, and a host where the difference is under 2 SE fails the claim.
92: 
93: If one meter passes and the other doesn't, the claim is inconclusive; `cost_disagreements` lists the pairs where they point opposite ways. Plan 2 predates this rule and was judged by its own.
94: 
95: **A phantom meter.** This workspace's VM offers a `power/energy-psys` counter, which opens without error but reads exactly 0 J idle and under load. A meter that is present but dead must be reported as unavailable, never as zero joules.

97: ## Trust model and limits
98: A verifier must cover these by reading the candidates' code:
99: - **The test labels are public.** scikit-learn's `load_digits()` is the test file. A `train.py` can carry the labels in as data and still reproduce byte for byte.
100: - **Counts are a claim for cooperative code.** Valgrind is always detectable from inside (its `LD_PRELOAD`, `/proc/self/maps`, its CPU), so a candidate could take a cheaper path when counted than when timed. Predictions are cross-checked between the runs; the work done isn't. Code that dispatches on CPU features (glibc's own `memcpy` included) is counted on its AVX2-or-lower path.
101: - **The time/Ir band** is relative to the lowest candidate and wide (30×). It catches gross hiding only.
102: 
103: Other limits:
104: - **The bubblewrap jail needs a kernel that lets an unprivileged user namespace mount `/proc`.** Z's kata container (kernel 5.10) refuses it. The fallback above needs Landlock ABI 4 (Linux 6.7+) instead; with neither, `loop.py` fails closed. Z re-measured plan 2 without the jail, after reading the code, and matched every accuracy and prediction exactly (`verifications/z-20261106/`).
105: - **The CPU pin isn't enforced (open, found by Z 2026-11-12).** The timer pins each candidate to one CPU, but a candidate may move itself to another; neither jail refuses that. On a host with unevenly loaded CPUs it could time faster than it earns. Effect not yet measured.
106: - **Tier 2 only.** Instructions and nanoseconds, not joules; native time is dominated by process startup at this task's size.
107: - **One task, one machine family per run.** Ir differs between x86-64 and arm64, so every Ir claim is per architecture.
108: - **SEs assume independent images.**
109: - **Size:** `loop.py` 666 lines, tests 331, `timer.c` 76, `confine.c` 99, `seccomp_filter.h` 113, `loop.yml` 133.

--- FILE: record/README.md ---
1: # record — spec card
2: 
3: **What it is.** The third brick: an append-only, hash-chained ledger of **plans** (a claim and the test fixed before it runs) and **verdicts** (the outcome, given by someone other than the claimant).
4: - **One writer.** Only `.github/workflows/record.yml` writes to it. Each run attests the exact range of entries it added: a Sigstore attestation in the public Rekor log, plus an OpenTimestamps proof in Bitcoin.
5: - **A stranger's checks:**
6:   - every entry is covered by the writer's attestations, with no gap;
7:   - every anchor is genuine;
8:   - every attestation the writer ever made, on any ref GitHub names, is in the ledger, or is explained by an orphan entry that publishes what it attested.
9: - **Why these anchors:** `experiments/anchors/RESULTS.md`, attacked by an outside verifier (`experiments/anchors/verifier1/`).
10: 
11: **Run.**
12: ```
13: python3 record.py verify          # chain intact? also lists open and overdue plans
14: python3 record.py head            # head seq and sha256
15: python3 record.py check-anchors   # every anchor right; writer's ranges cover 1..head; each run's commit
16: python3 record.py monitor         # every Rekor attestation by record.yml on any ref, vs the ledger
17: python3 -m unittest -v test_record   # 22 tests, <1 s
18: ```
19: - `verify` and `head` need only Python 3 (stdlib).
20: - `check-anchors` needs `sigstore==4.5.1` and `opentimestamps-client==0.8.0` (use a virtualenv), plus network access to blockstream.info and mempool.space.
21: - `monitor` needs network access to the GitHub API and Rekor. To judge orphan entries it needs a full (not shallow) git clone of the ledger branch; a shallow clone exits 2.
22: 
23: **Exit codes:**
24: - **0:** ok.
25: - **1:** something is wrong:
26:   - a ledger rule is broken;
27:   - an anchor is wrong;
28:   - the writer's ranges leave a gap or overlap, or don't reach the head;
29:   - an attestation is unexplained, or an orphan explanation is refused;
30:   - the ledger branch was force-pushed, or deleted (and recreated).
31: - **2:** can't check (missing library, network). `check-anchors` checks every anchor before deciding, so a problem in one doesn't hide a problem in another.
32: - **3:** unexpected failure. Wrong data never exits 3; a failure is never reported as a verdict.
33: 
34: ## How it's written
35: Proposals go in `ledger/inbox/NAME.json` as `{"kind": "plan" | "verdict" | "orphan", "body": {...}}`. A push to `main` that touches the inbox runs `record.yml`, which:
36: 1. **Runs exactly the commit that triggered it,** the one its certificate will name. If `main` has already moved on, it steps aside. The newer push's run, or failing that the daily run, takes the proposals. One writer runs at a time across all refs.
37: 2. **Refuses to add anything unless the writer's earlier attestations cover every existing entry,** so an entry written by hand is never vouched for later.
38: 3. **Ingests the proposals,** stamps the new head with OpenTimestamps, and refuses to attest if `main` has moved.
39: 4. **Attests the range it added:** predicate `{from_seq, to_seq, prev_sha256, head_sha256}`, with the head entry as subject. Then it checks every anchor and commits.
40: 5. **If it fails or is cancelled after attesting,** it pushes the bundle and the entries to the `ci-runs` branch (`orphans/<run>/`), so the orphaned attestation can be explained with its real statement and entries. That branch is owner-writable, so it's a convenience, not evidence.
41: 
42: The daily run also completes pending OpenTimestamps proofs, then runs `check-anchors --max-pending-hours 48`, so a proof still pending two days after its attestation turns that run red. (For its first five days, 6–10 Nov 2026, the upgrade failed silently: `shopt -s nullglob` deleted the unquoted `[bot]` email, so `git config user.email` ran with no value and exited 1. Found by the system review; every bot email in every workflow is now quoted.)
43: - Steps run under `bash -eo pipefail`, so a failing command in a pipe fails the run.
44: - `record.py` runs under `python3 -I`, so a file next to it can't shadow the standard library.
45: - `checkout` and `attest` are pinned by commit SHA.
46: - The pip packages are pinned by version, not by hash.
47: 
48: **Entries.** `ledger/entries/NNNNNN.json`: `{seq, prev, kind, written_at, body}`.
49: - **An entry's identity** is the sha256 of its stored bytes, and `prev` is the previous entry's.
50: - **The bytes must be exactly RFC 8785 (JCS)** of the entry, with no trailing newline, so any language can recompute them. Floats are refused (write them as strings). Keys must be ASCII, integers within ±(2⁵³−1), and lone surrogates are refused. Under these rules Python's `json.dumps(sort_keys, separators, ensure_ascii=False)` equals JCS. Fuzzed against the `rfc8785` library: 0 mismatches in 20,000 random objects (a reviewer repeated it); the test runs 3,000.
51: - **Duplicate keys,** non-canonical bytes, stray files, symlinks and directories are refused.
52: - **`written_at` is the writer's clock,** a claim. The anchors say when an entry really existed.
53: 
54: **Rules `verify` enforces:**
55: - seq runs 1, 2, 3…, and `prev` links each entry to the one before;
56: - body fields are known and well-typed;
57: - `by` is a lowercase ASCII handle, so look-alike names can't pass as different people;
58: - `verdict_due` must be a real date;
59: - a verdict names an earlier plan by seq *and* sha256;
60: - **one verdict per plan:** a re-run needs a new plan, so re-running until a result looks good shows up as several plans;
61: - a verdict's `by` differs from its plan's `by`. Handles are claims, not identities.
62: 
63: `verify` lists **open** and **overdue** plans. Completeness can't come from cryptography, so this list is how a missing verdict becomes visible.
64: 
65: **Orphan entries.** An attestation the writer made but the ledger doesn't hold (a run that failed or was cancelled after attesting) is flagged by `monitor` until an `orphan` entry `{by, log_index, reason, statement_b64, entries_b64}` explains it.
66: 
67: The orphan entry must **publish what the run attested**: the exact statement, plus the hidden entries themselves. The entries must be canonical, consecutive from the attested `from_seq`, chained from the attested `prev_sha256`, and hash to the attested head. The explanation is refused if:
68: - the statement isn't the one Rekor holds for that log index (its payload hash);
69: - the entries don't reproduce the attested range;
70: - the attested head was ever published on the ledger branch and later removed (needs a full clone).
71: 
72: So hiding an attested verdict means publishing it inside the orphan entry. The `reason` is a claim; the entries are the evidence.

157: ## Trust model and known limits
158: - **No anchor proves completeness.** A run that never reaches the writer leaves no trace: a private run, a fork, code outside CI. Covered: every run of `record.yml` in this repo, on any ref the monitor can name, published or not. Pre-registered plans make a missing verdict visible. Re-measurement (item 4) is the backstop for content.
159: - **The owner controls the inbox and the code.** A proposal can be deleted before any run; only pre-registered plans and the overdue list catch a missing verdict. The writer runs the repo's own `record.py`, so a code change shows up only as `writer_code_changed: true` between two runs. A stranger has to read that diff; nothing judges it automatically. The pip packages are pinned by version, not by hash.
160: - **An attestation says** "record.yml at commit X added these entries". It doesn't say they are true.
161: - **Ref discovery depends on GitHub** (branches, tags, PRs, the activity log). Deleting the repo erases that list. Rekor keeps the attestations, but a stranger would need to scan the log (rekor-monitor). Rekor v2 has no search index; the public instance stays on v1 for now.
162: - **Orphans.** A failed push after attesting leaves an orphan that stays red until explained. That's intended: the failure is part of the record.
163: - **The monitor is a command, not a service.** Someone has to run it. A scheduled run from outside the owner's control (Z, or another account) is the next step.
164: - **OpenTimestamps** proofs are pending for hours. Verifying through the explorers trusts that two operators serve the real chain.
165: - **Size:** `record.py` is 630 lines, the tests 235, `record.yml` 127. Most of it is defences, as with the counter.
