`python3 -I audit/spine/replay.py worker/transitions.py audit/2026-11-17/queue.json` (main's transitions.py;
pilot branch at 4420bdf, full history; zero model calls; 15 s). Raw output: `replay-2026-11-25.json`.

## Result: the model fits; the recording does not (strict criterion FAILED)

**B. Git history as events: fits.** 1,552 snapshots of queue.json; 1,360 status changes; **1,356 (99.7%) are
moves the state machine allows**. The 4 others (waiting on the owner -> escalated) are all in the commit that
introduced the state machine. State changes in this system already behave like events through one state machine.

**A. The items' own run logs as events: 230 of 339 items (68%) rebuild exactly. 109 do not.**

Moves logged from a state the log never entered: `redo` from open 28, `resplit` 10, `review_applied` 6, `solved` 5.
57 run entries carry no outcome at all.

Who wrote the last unlogged change (commit subject prefix), 109 items: worker 37, `queue` (chat sessions and owner
edits) 25, `audit` 22, tier (Haiku) 10, claude-shift 5, before history 8, splitter 1, `audit queue` 1.

## What it means

The state is complete only in git snapshots, and the causes live only in free-text commit subjects. A new agent
cannot read *why* an item is where it is from structured data for a third of the queue. This is the spine problem
in miniature, and it can be fixed locally before any service exists.

## Next (P37b)

Every status write (claim, release, tier move, chat or owner edit, splitter, audit) appends one structured event
`{at, actor, from, outcome, to, reason}` through `worker/queue_ops.py move`; a writer that bypasses it fails a
test. Pass: replay A reaches 100% for items changed after the fix. Only then build the live spine (P36 test 2).
