=== Interpretation ===
Test 1 (strict) is the safe verifier: passes only for the real SAN + repo + ref + trigger.
Test 2 (wrong ref): the verifier EXPECTS a different ref than what the cert claims; FAILS — good.
Test 3 (loose: no --ref, no --trigger): still PASSES because the --cert-identity is the FULL SAN including @ref. The cert's SAN includes the ref, so even without --ref, the verifier implicitly accepts whatever ref the cert claims. A fork or different-branch attestation would also pass — the verifier is NOT pinning the ref.
Test 4 (cert-identity without @ref): likely FAILS because sigstore-python does exact-match on the SAN string.
Test 5 (wrong repo): FAILS — sigstore-python checks the Source Repository URI OID extension against --repository.
Test 6 (different workflow path): FAILS — SAN exact-match.
Test 7 (no --repository): FAILS — sigstore-python requires --repository for github verify mode (or it can't validate the OIDC issuer context).

=== Takeaway ===
A verifier who runs 'sigstore verify github --bundle b --cert-identity URL@REF --repository REPO --offline sha256:D' is safe.
A verifier who OMITS --ref and --trigger is *not* safe against an attacker who controls a different branch in the same repo, because the cert's SAN includes whatever ref the attacker ran on, and the loose verifier accepts it.
A verifier who omits --repository is unsafe against forks (sigstore-python refuses to verify without --repository in github mode, mitigating this).
