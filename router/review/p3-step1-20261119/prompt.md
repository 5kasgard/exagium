```
# P3 step 1: outside-strength families on the three label tasks (plan, fixed before any run)

Written 2026-11-19 before the new candidates were written or run. Commit time is the registration time.
Dev split only; the test split stays closed (no ledger plan).

## Why
An outside review (2026-11-19, reviews/44470377631, finding 2) found the suite's baselines too weak to say anything:
only majority, linear and a 16-unit MLP. Transfer step 1 found family rankings change across tasks. The queue's Q54
hypothesis (cheapest artifacts are those whose structure matches the hardware's own primitives, e.g. lookup tables)
was weakened by the logic-gate network on text and tabular data, but lookup-table families were never tested.

## What runs
Tasks: optdigits, text (next character, 65 classes), adult (tabular), as built by `tasks/build.py`.
Existing candidates, unchanged: majority, label-linear, label-mlp16.
New candidates (numpy training, C inference, deterministic, single thread, the same contract):
- **label-gbdt**: gradient-boosted trees, one multi-output tree per round (softmax gradients, second order), splits
  on byte values. Outside-strength baseline for tabular data (published comparisons find tuned tree ensembles strong
  on tabular data; to be checked against research card R5 when it lands).
- **label-knn**: k nearest neighbours, per-column distance by the card's types (ordinal: scaled absolute
  difference; categorical: mismatch).
- **label-wisard**: a WiSARD n-tuple classifier (weightless, lookup tables only) with thermometer or one-hot bits and
  bleaching. The Q54 test family.

Tuning, the same for every new family: the tuning split is the last 20% of `train.in` in file order. Each new family
chooses at most 6 settings on it (fixed grids in its `train.py`), then retrains on all of `train` with the chosen
one. Existing candidates keep their fixed settings (a stated limitation: the new families get a tuning budget the old
ones do not).

## Measures (runner/run.py, as for P2)
Per candidate and task: per-item scores (kept), dev accuracy and SE, simulated instructions per item (cachegrind),
native ns per item. Paired comparisons use per-item outcomes: SE of the difference from paired items.

## Questions and rules (fixed now)
1. **Floor margin** (review finding 2): a task stays in the suite only if its best family beats majority by at
   least 3 paired SE. Forecast: holds on all 3 (p = 0.97).
2. **Does an outside-strength family change the picture?** For each task, does the best new family beat the best of
   linear and mlp16 by more than 2 paired SE? Forecasts: adult (gbdt) p = 0.65; optdigits (knn) p = 0.25; text p = 0.35.
3. **Q54 for lookup tables.** On each task, wisard is "matched" if its accuracy is at least that of the more accurate
   of linear and mlp16 minus 2 paired SE, and "leads on cost" if, when matched, its instructions per item are lower
   than that family's. Supported if matched and leading on both non-digit tasks (text and adult); weakened if only on
   optdigits or on none; mixed otherwise. Forecast: supported p = 0.2, mixed p = 0.3, weakened p = 0.5.
4. **Reproduction**: every new candidate's training must give identical weights twice (`run.py reproduce`). A
   candidate that does not reproduce is reported and excluded from 1-3.

Forecasts are Claude's, stated so calibration can be scored later (queue P23, P11).

## Not claimed by this step
Anything about the test split; any task beyond these three; tuned versions of linear and mlp16.
```

```
# P3 step 1 result: outside-strength families on optdigits, text and adult (2026-11-19)

Plan and forecasts fixed before any new code existed: [PLAN.md](PLAN.md) (8408ef2). Families: 8f46c37. CI: runner run
44486290814 (ubuntu-24.04, bubblewrap jail), raw output in [ci/](ci/); the rules applied by [decide.py](decide.py) in
[DECISION.md](DECISION.md). Dev split only; every number below holds for these three tasks, this host type and these
training recipes.

## Answers to the fixed questions
1. **Floor margin: holds on all three tasks** (best family over majority by 85, 38 and 20 paired SE).
2. **An outside-strength family changes the picture on two of three tasks.** Gradient-boosted trees beat the best of
   linear and mlp16 on text (0.392 vs 0.338, +10.4 paired SE) and adult (0.866 vs 0.859, +2.4 SE), not on optdigits
   (0.979 vs 0.977, +0.5 SE). The accuracy costs instructions: on text the trees use 131,154 instructions per item
   against linear's 7,360 (18 times), on adult 7,570 against mlp16's 2,325 (3.3 times).
3. **Q54 for lookup tables: weakened.** WiSARD (lookup tables only) was less accurate than the better of linear and
   mlp16 on every task (-3.1, -25.5 and -7.0 paired SE) and also used more instructions per item (34,076 vs 8,686 on
   optdigits; 119,869 vs 7,360 on text; 20,923 vs 2,325 on adult). With the logic-gate network's result on text and
   tabular data (transfer step 1), both lookup-style families tested so far weaken the hypothesis that structures
   matching the hardware's own primitives are cheapest at matched accuracy. Families not yet tested: constraint
   propagation, Tsetlin machines, cellular automata, event-driven.
4. **Reproduction: all three new families gave identical weights twice on every task.**

## Forecasts (Claude's, fixed in PLAN.md) against outcomes
| question | forecast | outcome |
|---|---|---|
| floor margin on all 3 | 0.97 | yes |
| new family beats old, adult | 0.65 | yes |
| new family beats old, optdigits | 0.25 | no |
| new family beats old, text | 0.35 | yes |
| Q54 supported / mixed / weakened | 0.2 / 0.3 / 0.5 | weakened |

Brier score over the four yes/no forecasts: 0.152 (lower is better; 0.25 is what always saying 0.5 scores). One run is
far too few to judge calibration; this row is the start of a record (queue P23, P11).

## Limitations, stated
- **Grid edges.** kNN chose k = 15, the largest value in its grid, on text and adult; gradient-boosted trees on
  optdigits chose 293 rounds of the 300-round cap during tuning (text: 260; adult: 59, both inside the cap; from the
  deterministic tuning logs of a local run, since CI keeps no training logs). Both families might do better with wider grids. The
  grids were fixed in the plan and were not changed after local dev scores were seen.
- **Unequal tuning.** The new families chose settings on the tuning split; linear and mlp16 use fixed settings.
- **Categorical columns** are split by trees on their byte codes (an arbitrary order), and compared by kNN as equal or
  not; WiSARD uses one-hot bits for the 8 or 16 most frequent values only.
- **Cost** is instructions and native time per item on one CI host type; kNN's cost grows with the training set.

## What this changes
- The suite's strongest baseline on text and tabular data is now gradient-boosted trees, at a much higher cost per
  item: an accuracy-cost frontier, not one winner. Later claims on these tasks are measured against it.
- Q54 needs a new kind of evidence or should be narrowed; it is not supported by any family tested so far.
```
