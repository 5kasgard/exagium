# Claude report (2026-11-15): testing Gemini's analysis, and where mlp16's time goes

**Host.** Intel Xeon @ 2.30 GHz nominal (family 6, model 173, from `reference/host-lscpu.txt`), 2 vCPUs in a KVM VM, no hardware counters. `bin/clock` measured 3.79–3.84 GHz under load. 48 KB L1d per core, gcc 13.3, `-O2 -std=c11 -ffp-contract=off`.

**Method.** N = 95,600 (`data/big.bin`), pinned, interleaved rounds. Each figure is the median (IQR) of (t(N) − t(0)) / N, compared only within one run. The raw times are in `results/*.json`.

## 1. Gemini's predictions
Run `results/gemini-variants-xeon.json`, 21 rounds:

| variant | what changed | ns/img | Ir/img | predicted | verdict |
|---|---|---|---|---|---|
| mlp16 | — | 80.8 (77.7–85.4) | 645 | — | — |
| mlp16_l1only (Gemini's H3) | layer 2 and argmax removed | 63.4 (57.3–65.6) | 403 | 25–30 | layer 1 is the larger cost (Gemini's outcome B) |
| mlp16_bl_tree (Gemini's) | branchless layer 2, two-way tree, branchless argmax | 81.8 (78.8–91.3) | 695 | 49–55 | no gain |
| mlp16_argmax_bl | branchless argmax only | 80.3 (77.1–86.6) | 684 | — | no gain |
| mlp16_bl_single_argmax_bl | branchless layer 2 in one chain, branchless argmax | 80.8 (77.9–87.2) | 704 | — | no gain |

**All three branchless variants print output identical to mlp16** on all 95,600 images, the two-way tree included, and also with the weights trained on 75% of the file.

**Simulated mispredicts per image** (cachegrind): mlp16 3.21, argmax_bl 2.92, **bl_tree 1.07**, l1only 0.07. bl_tree removes two-thirds of them with no speedup.

**H9 (mispredicts) and the layer-2 add chain are ruled out on this host.**

**Gemini's correction to H4 is confirmed.** GCC never stores `h[]`; it extracts lanes with `pextrw`. Store forwarding is ruled out.

## 2. Layer 1: address dependence
Run `results/layer1-split-xeon.json`, 21 rounds, Ir from valgrind:

| variant | ns/img | Ir/img |
|---|---|---|
| mlp16_null: I/O, validation and output only | 33.8 (31.3–37.6) | 56 |
| mlp16_l1only | 57.0 (55.3–63.9) | 406 |
| mlp16_l1_fixrow_indep: row from the image index, not the pixel; pixels still loaded into a checksum | 54.9 (52.9–57.9) | 451 |
| mlp16_l1_fixrow_dep: row still waits on the pixel load, fixed rows | 63.1 (58.9–66.8) | 606 |
| mlp16 | 77.7 (73.7–83.4) | 645 |

**H2 (address dependence) was called ruled out here; that was wrong** (2026-11-17 audit). The unpaired medians differ by about 2 ns with overlapping IQRs, but paired per round the dependence-free variant is 3.8 ns/img faster in 18 of 21 rounds (sign test p = 0.0015). It is a small, consistent effect: unresolved, not ruled out.

**Two design errors of mine were caught before any timing was read:** a checksum written to a lane that's never read, which let GCC delete the loads, and fixed rows that made layer 1 identical for every image. Both were fixed, checked with objdump (`movzbl` and `paddw` counts) and valgrind.

## 3. The input read: H10, new
mlp16 reads all N images into one freshly allocated n × 64 B buffer, 6 MB at N = 95,600. Each 4 KB page costs a first-touch page fault, which is expensive on a VM. That cost scales with N, so it lands in the per-image slope. It is also kernel time, so the instruction meter doesn't see it.

**Page faults per run at N = 95,600** (`getrusage`, median of 9): mlp16 1,670, linear 171, i.e. about 1,500 extra, one per 4 KB of the buffer.

**The variant** `mlp16_chunked` is the same compute, reading input in chunks of 1,024 images through one reused 64 KB buffer. Its output is identical for N = 0, 1, 956, 1,023, 1,024, 1,025 and 95,600; it rejects bad pixels; it runs 644 Ir/img against 648.

Run `results/io-split-xeon.json`, 21 rounds:

| | ns/img |
|---|---|
| linear | 179.3 (177.4–203.8) |
| linear_null: same per-image `fread`, no compute | 16.7 (15.5–17.7) |
| mlp16 | 84.5 (78.8–88.4) |
| mlp16_null | 41.5 (36.6–43.0) |
| **mlp16_chunked** | **57.3 (54.8–61.9)** |

**Paired within rounds:** mlp16 − mlp16_chunked = **28.5 ns/img** (IQR 21.6–32.8). The same program, with identical instructions and predictions, is 32% faster when it doesn't fault in a 6 MB buffer.

## What the data says the cause is
**1. Mostly the I/O pattern, not the inference.** About 28 ns of mlp16's ~80 ns per image at this N is page faults on its input buffer. These are kernel costs the instruction meter cannot see. With each program's I/O removed, the gap in instructions per ns falls from about 2.6× to about 1.7×.
   - Confidence: high on this host. A separate agent repeated it from a fresh clone: mlp16 − mlp16_chunked = 31.2 ns/img (IQR 26.3–35.9, positive in all 15 rounds), with 1,594 against 116 page faults per run and identical output for N = 0, 1, 1,023–1,025, 2,049 and 95,600.
   - That agent noted a fair limit: a smaller buffer could also help through cache locality, which isn't separated from the fault cost.
   - It may differ where page faults are cheaper, on bare metal or with transparent huge pages.

**2. The remaining 1.7× is mainly linear being unusually fast per instruction (H6).** Its compute runs at about 5.9 instructions per cycle, near the core's width: simple loads, adds and fused compare-and-branch pairs. mlp16's compute at about 3.4 per cycle is ordinary for code mixing loads, vector adds, conversions and shuffles.
   - Confidence: moderate. Without counters, uops per port can't be confirmed. Gemini's static floor (100–134 cycles) is below mlp16's compute-only ~175 cycles, a gap of ~40–75 cycles still unattributed.

**3. Ruled out on this host:**
- dependency chains, by interleaving (earlier work);
- branch mispredictions (H9);
- the layer-2 add chain;
- store forwarding (H4);
- (H2 removed from this list in the 2026-11-17 audit; see section 2)
- L1 capacity (mlp64 runs at the same rate).

## Consequences beyond this puzzle
- **The project's meters.** Native time includes kernel work, such as page faults and reads, that the instruction meter can't see. A candidate's input strategy can move native time by about 30% without changing a single counted instruction.
  - loop.py's dev runs (N = 956, a 61 KB buffer, about 15 pages) feel this far less than N = 95,600 does.
  - It still belongs in the loop spec card's limits. It also sharpens the "two meters" table there: part of what that table attributed to slow instructions was kernel work.
- **The steady-state LGN comparisons in pilot 2** used programs that also allocate n × 64 B input buffers, so the same cost is in those numbers too. Both mlp16 and lgn_d carry it, so their ranking shouldn't change, but the absolute ns/img should be read with this in mind.

## Reading the three reports together (Gemini, GLM, this one)
**All three agree on what is ruled out:** dependency chains (NB interleave), mispredicts (H9; GLM's fully branchless version was 19–21% *slower*), store forwarding (H4; `h[]` is never stored, a compiler fact found by both Gemini and GLM), address dependence (H2), code size (H5) and VM noise (H7).

**Gemini's quantitative prediction is falsified twice.** It said layer 2 and the argmax dominate, and predicted 25–30 ns for layer 1 alone. GLM measured layer 1 at 71% of the time and I measured about 78%.

**GLM's unattributed ~60 cycles in layer 1 is probably the input buffer (H10).**
- Its `h3_l1only` reads all N images into one fresh n × 64 B buffer (`reports/glm-20261115/src/h3_l1only.c`, line 39), so its "layer 1 ≈ 171 cycles" includes the page-fault cost.
- On my host that cost is 28–31 ns/img, about 107–118 cycles.
- On GLM's host it is unmeasured; the kernel is 5.10, and fault cost varies.
- Test: run `programs_io.json` there.

**GLM's claim that layer 2 is bound by its serial add chain isn't supported by two results.**
- Gemini's two-way tree halves that chain's depth and was not faster here: 81.8 against 80.8 ns, with overlapping IQRs.
- Interleaving images, which overlaps different images' chains, also didn't help.
- At steady state, an out-of-order core can run one image's layer-2 chain under the next image's layer 1. A latency-bound chain would have shown a gain in at least one of those tests.
- Layer 2's ~48–79 cycles more likely reflect throughput: about 12 conversions, shuffles and 36 vector multiply-adds per image, plus stack loads. That is unconfirmed without counters.

**GLM's compiler point is a correction to the brief.** gcc 14.2 gives linear 4,188 Ir/img against gcc 13.3's 3,812, and the per-instruction gap is 1.86× there against 2.4× here. The size of the puzzle is compiler-dependent.
