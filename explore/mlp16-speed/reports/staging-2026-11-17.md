# Staging only the needed images (2026-11-17)

**Question (owner):** instead of loading all images, or chunking by an arbitrary limit, load only the images the run, or the step, needs. Does that beat the chunked fix?

**Host:** this session moved to a different VM. It is an Intel Xeon @ 2.10 GHz nominal, measured at 2.69–2.81 GHz by `bin/clock`, 2 vCPUs, transparent huge pages = `madvise`. Compare only within one run.

## 1. Staging alone (no classifier)
Every program in `src/stage_null.c` validates every pixel and prints one digit per image. Only how the N needed images are staged differs. Run `results/staging-xeon.json`, 21 rounds, N = 95,600; page faults are a median of 5 runs, from `getrusage`.

| STRAT | how | ns/img (IQR) | page faults/run |
|---|---|---|---|
| 1 | one fresh n × 64 B buffer, one `fread` (mlp16's way) | 56.2 (45.6–65.5) | 1,662 |
| 5 | as 1, 2 MB-aligned, `madvise(MADV_HUGEPAGE)` | 35.0 (28.2–41.7) | 174 |
| 2 | chunks of CH images, `fread`, one reused buffer: CH = 16 / 64 / 256 / 1,024 / 4,096 / 16,384 | 16.7 / 17.7 / 13.5 / **12.8** / 13.8 / 18.7 | 168–425 |
| 6 | as 2 with `read(2)`: CH = 16 / 64 / 256 / 1,024 / 4,096 / 16,384 | 33.0 / 14.2 / 14.1 / **11.5** / 14.3 / 17.4 | 168–425 |
| 3 | `mmap` exactly n × 64 B of the file, no copy ("load only what's needed") | 14.6 (12.3–18.6) | 262 |
| 4 | as 3, plus `MAP_POPULATE` | 13.2 (7.5–16.7) | 262 |

All 16 programs print identical output at 13 values of N, from 0 to 95,600, including partial blocks (`results/staging-evidence.json`). Page faults are recorded there too; the table's fault counts now match that file (corrected in the 2026-11-17 audit: an earlier version showed figures from a separate, unsaved run: 1,663 / 169–424 / 167–424).

**Kill criterion, set before the run:** an alternative counts only if it beats chunk-1024 beyond the IQRs. None does.

**Paired against chunk-1024, per round** (`results/staging-evidence.json`):

| comparison | ns/img (IQR) | rounds positive |
|---|---|---|
| bigbuf | +41.8 (34.8–53.5) | 21/21 |
| mmap | +1.9 (−1.2–6.6) | 14/21 |
| mmap + populate | +2.5 (−6.4–4.4) | 11/21 |
| read-1024 | −0.1 (−7.3–3.6) | 8/21 |
| read-16 | +19.8 (12.1–22.0) | 21/21 |

**What this test can and can't show** (correction after review). Staging alone is about 1.2 ms on top of a 2.2–2.6 ms process start, so these paired IQRs are 5–14 ns wide on a ~12 ns quantity. This test can only detect differences of about 4–5 ns or more. So: no strategy beats chunk-1024 by more than about 5 ns/img in staging alone. The full-classifier comparison below is tighter.

## 2. The real classifiers
Run `results/staging-full-xeon.json`, 21 rounds, N = 95,600. Ir is from valgrind. Paired differences are per round, from the same run.

| program | ns/img (IQR) | Ir/img |
|---|---|---|
| mlp16 | 106.8 (102.6–110.3) | 644.7 |
| mlp16_chunked (CH 1,024) | 73.7 (71.0–75.5) | 641.1 |
| mlp16_mmap (`src/mlp16_mmap.c`) | 73.4 (71.6–74.8) | 644.7 |
| lgn_d (pilot 2, `src/lgn_orig.c`; weights in `weights/lgn_d.bin`) | 68.4 (64.2–72.1) | 291.4 |
| lgn_d_blockread (`src/lgn_blockread.c`: reads only the 1,024-image block it is about to classify) | 36.9 (35.6–38.5) | 288.1 |

**Paired differences:**
- mlp16 − mlp16_chunked = 32.5 ns/img (IQR 28.5–36.1), positive in 21 of 21 rounds.
- mlp16 − mlp16_mmap = 32.0 ns/img (IQR 29.8–37.3), 21 of 21.
- lgn_d − lgn_d_blockread = 29.5 ns/img (IQR 26.2–33.5), 21 of 21.
- mlp16_chunked − lgn_d_blockread = 36.7 ns/img (IQR 35.2–38.8), 21 of 21.

**Identical output:** the three mlp16 variants print the same output, and so do both lgn_d variants, at N = 0, 1, 956, 1,023, 1,024, 1,025, 2,049 and 95,600. A pixel of 17 inside N makes both new variants exit 2, as the originals do.

## Claims (worded after the adversarial review)
1. The cost was **how** the images were held, not loading extras. mlp16 already reads exactly N images (`fread(x, 64, n)`).
2. Holding them in one fresh buffer costs more than a reused buffer of 256–4,096 images, or a mapping:
   - 42 ns/img in staging alone (paired with chunk-1024);
   - 32 ns/img in the full mlp16.

   Very small chunks don't get all of it: `read` in 16-image chunks is 20 ns/img slower than chunk-1024.
3. "Only what's needed" (`mmap` of exactly n × 64 B, no copy) **ties** with a reused 1,024-image buffer in the full classifier: −1.1 ns/img (IQR −3.3 to 3.2), positive in 9 of 21 rounds. This comparison could have detected a difference of about 3 ns/img; none appears.
4. For lgn_d, reading only the block about to be classified cuts **46% of its per-image time** (36% of wall time at N = 95,600), with instructions unchanged (291 → 288 Ir/img). After the fix it is **2.0× faster than mlp16_chunked** (and 2.9× faster than mlp16 as committed) at steady state, on this host.

## Limits
- **One host (a VM), steady state only (N = 95,600).** At loop.py's N = 956 the buffer is 61 KB, so the effect should be much smaller; not measured here.
- **What the penalty is.** It comes from faulting in fresh anonymous memory, with transparent huge pages in `madvise` mode. Asking for huge pages (STRAT 5) removes about 21 ns of it on its own, but stays slower than a small reused buffer. Hosts with THP set to `always`, or on bare metal, may show a smaller penalty.
- **Warm page cache only.** Every run read a file already in the page cache. `mmap` from a cold cache could cost more than `read`; not measured.
- **The jail.** `mmap` is not on the fallback jail's seccomp deny-list (`loop/seccomp_filter.h`). It still needs a test inside the jail before any candidate relies on it.
- **Review.** One adversarial review by a fresh Claude agent (Opus, same family as the author), so its verdict is direction, not independent evidence. It recomputed every number from the raw JSON, rebuilt every binary, and checked output identity at 14 values of N and 4 bad pixel values. It found 1 major and 5 minor issues, all fixed here.
- The weights for lgn_d are pilot 2's, trained on 75% of the file; mlp16's are the committed full-file weights. They are compared for speed, not accuracy.
